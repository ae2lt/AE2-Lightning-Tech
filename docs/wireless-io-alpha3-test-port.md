# alpha.3 无线接口测试移植

## 普通批量与快速响应（2026-09-07）

本轮基线为 `71b3d35fe7ecae9c937718575836badc48885715`，修改限于过载接口。
样板供应器、外部容器实现、持久缓冲所有权及单次配置限额保持原行为。

- NORMAL 用实际可观测库存 / 输出槽容量和传输速率计算半缓冲等待时间。
  速率为本次移动量除以距离上次完整补满 / 取空的时间，取最近两次中较快的速率。
  批次增大本身不会被当作加速；满槽耗尽、部分传输时优先下一 tick 观测。
  源库存或电力缺失先及时重试一次，再恢复线性退避，不能误用目标活跃期的逐 tick 空轮询。
- FAST 复用导入已有的成功 / 空读预测规则：成功后下一 tick 检查，只有真实空读 / 拒收才等待。
  周期性生产不要求每 tick 空探测，连续生产则允许每 tick 传输。
- 物品导入在原有一次槽位遍历中观察已使用输出槽，各槽等待时间取最小值；空白或过滤掉的槽
  不算作可用输出余量。精确过滤的普通物品导入也走这条逐槽路径，仍执行完整过滤和导出黑名单。
- 普通物品导出首次及每隔至少 100 tick 做一次整目标校准，用公共 `IItemHandler` 读取当前库存；
  `isItemValid` 为 false 的输出专用槽不计入输入库存。所有配置 key 共用这一遍扫描。
  快速模式没有这项扫描，也不创建库存速率对象。每个 key 的普通补货成本为 O(1)，
  目标调度仍用现有时间轮，没有新增 Map、排序或第二套调度队列。
- 非物品或自定义 MEStorage 若无法可靠观测容量，导入保留及时取走策略；导出只使用已实际接受过的
  填充量作为容量下界，不猜测隐藏槽位。所有导出类型均区分普通批量和快速响应。
  此次没有用物品容器的容量推测第三方流体或自定义资源的输出空间。
- 输入库存与槽容量来自能力接口的公开信息，不能识别第三方机器内部的配方依赖；未通知的容量缩减、
  突发输出及任意变速仍需下一次观测才能识别。此策略不承诺所有未知负载下零瞬时阻塞。

验证：910 项 JUnit 全通过，完整构建通过。容量 100、消耗 10/t 的稳定模型，普通每 5 tick 补 50，
快速每 tick 补 10；初始库存 0 / 50 / 90 / 100 均覆盖，单次限额 10 时两种模式均每 tick 传输。
原有 80% 变速吞吐要求、缺货恢复、物品组件、部分取出及所有权测试保留。

新增四项真实网络测试覆盖本地 / 无线的导入 / 导出。无线各 1024 个目标，每目标 27 种物品，
每槽容量 64、每 tick 生产 / 消耗 10；普通模式约每 3 tick 传一次，快速每 tick 传一次。
测试在同一运行中 NORMAL → FAST → NORMAL，再提高至每槽每 tick 64，稳态阻塞为 0，逐 key 守恒。
原有两项批量调用预算测试改为检查 NORMAL，保留其 180 tick / 最多 60 次物理调用上限；
FAST 的响应和生产效率由上述真实切换测试及有限机器模型单独约束。

性能场景 `import-buffered-normal-1024x27` 使用相同 1024×27 个容量 64 的槽，每 tick 每槽生产 10。
与满速 FAST 的 `1024x27` 场景分开运行；前者验证减少容器调用的收益，后者检查必需逐 tick
传输的路径是否回退。两侧使用完全一致的 GameTest 夹具，供应器与容器实现未修改。

## 复现

要求 Java 21，依赖已下载到 Gradle 缓存，两个独立工作树。
初始化脚本为双方使用相同的最小运行依赖、512 MiB 初始堆和 2 GiB 最大堆。
专用性能任务仅编译、注册移植的两个 GameTest 类，双方均为 23 项；
比较脚本记录并校验注册数量。普通语义运行仍包含 alpha 自己的回归测试。

```sh
./gradlew test compileJdbJava --offline --no-configuration-cache
./gradlew runGameTestServer --offline --no-configuration-cache \
  -I scripts/wireless-io-benchmark.init.gradle

python3 scripts/run-wireless-export-benchmark.py \
  --baseline /absolute/path/to/test-worktree \
  --profiles export-empty-1024 export-mismatch-1024 export-continuous-256x27 \
  --runs 5 --output build/reports/wireless-export-ab
```

输出目录必须是新目录，以免覆盖旧结果。每轮按 control/stress 顺序，逐一运行两版，
偶数轮交换版本顺序；不同时运行两台服务器。每次 Gradle 任务启动新的 GameTestServer JVM。
保存源码散列、Git HEAD/dirty 标记、命令日志、JSON 及逐 tick CSV；运行期间拒绝源码变化。
`--runs 1` 仅用于试跑，不能作为五轮验收。

三种场景均预热 200 tick、采样 1200 tick，外层计时包括 I/O 资格检查。
空配置和类型不匹配按每版十次空闲重复测量，不做 control 相减；持续发配按五组配对控制。
使用原比较器的吞吐、守恒、尾延迟及内存门槛，I/O P99 预算为 4 ms。
GameTest 按其服务器运行方式推进 tick；capacity TPS 是根据测量耗时计算的容量指标。
这些测试不代表包含第三方机器和完整模组包的实际服务器 MSPT。

## 导入观测规则重做（2026-09-07）

本次比较基线为 `bcf8f59113f343380dd76e3a28e4c67562c208c0`。
问题不在传输或缓冲所有权，而在观测含义：导入成功时拿到的是“这次取走了输出”，
相邻两次取走的间隔包含生产、轮询等待、停产及输出堵塞，不能直接当作机器周期。
在无通用内容变更通知的容器上，若两台机器在上次空读前完全相同、随后只有一台开始生产，
调度器在下次读取前无法区分它们。因此不承诺同时实现任意变速即时响应和零额外轮询。

接口的 `CooldownTracker` 采用统一规则，不再复用供应器的推送失败预测器：

1. 成功取走输出后，下一 tick 再取；连续有输出就持续工作。
2. 只有实际空读才允许使用等待预测；单次长间隔不足以改变生产频率判断。
3. 用最近三个间隔的中位数预测下一次读取。三个是抵抗单个异常间隔的最小奇数窗口；
   使用整数比较，两个历史整数，无列表、排序、Map、hashCode 或逐 tick 分配。
4. 保留原有 100-tick 活跃观测范围及空闲线性退避，上限 FAST 20 / NORMAL 80 tick。
   模式变化清空观测。一次停产后的额外空读属于重新观测成本，不设置额外恢复状态机。

移除了临时尝试的恢复次数、热身次数和补探测间隔；轮询状态直接存于原 tracker，
省去每个 tracker 的一个 `TransferPollSchedule` 对象。
供应器仍使用原推送策略；接口每个导出 key 的 `TransferCadence` 不变。
导入取走、持久缓冲、ME 回灌及回压唤醒的代码均不变。

这仍是有限观测下的估计，连续多个异常间隔及任意未知变速不在确定性保证内。
既有 100-tick 学习边界也仍存在；本次没有通过扩大该边界或提高空闲轮询频率换取恢复。
